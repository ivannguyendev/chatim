# Decision Log D262–D268: M7: media

## 17.22 M7 phase P1 — upload nhiều phần (2026-11-06 → 2026-11-07, owner duyệt)

| # | Quyết định | Lý do |
|---|---|---|
| D262 | (Owner 2026-11-06) **Media là module nhúng `modules/media` trong chat** (khuôn Mention, D177, D182): module giữ riêng collection `media_uploads`, đăng ký `MediaService` trên gRPC server của chat, gateway chuyển lệnh tới node chat bất kỳ như lệnh `request` khác; chat chỉ import `modules/media/mediaapp`. Chỉ dùng giao thức S3 chuẩn; production là AWS S3 | Byte file không đi qua server nên module chỉ gọi vài lệnh S3 nhỏ. Không làm app riêng `apps/media` với database riêng: thêm container, user database và đường gateway → media → chat khi chưa có nhu cầu (chỉ cần khi quét file GB trên server). Không đặt trong gateway: gateway không có database. Không gắn với một nhà cung cấp: dev chạy server S3-compatible, production AWS S3 |
| D263 | **Thay một phần bởi D267 (khoá ngẫu nhiên), D272 (khoá file công khai).** (Owner 2026-11-06) **Hợp đồng upload:** byte đi thẳng từ máy lên S3 bằng multipart. Server quyết cỡ phần và số phần từ cỡ khai (có trần cỡ phần, số phần, số luồng song song, đều là config) và ký URL từng phần ghim `Content-Length`; khoá object `{tenant}/{user}/{yyyymmdd}/{ngẫu nhiên}` với tenant và user lấy từ token; máy gửi ETag mọi phần khi `CompleteUpload`, server kiểm đủ phần 1..n rồi `HeadObject` kiểm tổng cỡ (lệch thì xoá object); `CompleteUpload` gọi lại an toàn (`NoSuchUpload` → `HeadObject`); gateway giới hạn `GetPartURLs` theo user, user + IP, user + IP + thiết bị (`sid`) | File vài GB không đi một lần PUT trên mạng di động. Không để máy chọn cỡ phần: server mới ghim được cỡ từng URL và kiểm lúc đóng. Không để server gọi `ListParts`: thêm lệnh S3 và phân trang khi S3 tự kiểm ETag. S3 cho đóng phiên với một tập con các phần (spike M7 P1) nên kiểm đủ phần và tổng cỡ là bắt buộc. Giới hạn đặt ở gateway vì chỉ gateway thấy IP và thiết bị |
| D264 | (Owner 2026-11-06) **Kho object:** hai bucket do hạ tầng tạo sẵn, code không tạo bucket, luật hay CORS. `processing` nhận upload (huỷ multipart dở sau 1 ngày, xoá object sau 30 ngày); `completed` giữ file đã gắn tin. Media lỗi (config sai, thiếu bucket, sai key, S3 sập) chỉ làm media chưa sẵn sàng: module kiểm `HeadBucket` lúc khởi động và định kỳ, lệnh upload trả `UNAVAILABLE`, `GetClientConfig` báo tắt, có metric và alert; chat không bao giờ dừng vì media | S3 lỗi không được kéo mất nhắn tin, nên không chặn chat khi khởi động. Code không tạo bucket để key của chat không cần quyền tạo bucket ở production. Không làm bucket thứ ba cho file của tin đã xoá: chỉ đánh dấu, chính sách xoá làm sau. Không để worker tự quyết file mồ côi: luật lifecycle của `processing` dọn file không gắn tin |
| D265 | (Owner 2026-11-06) **`ChatService.GetClientConfig` là API config chung cho máy:** giới hạn tin (text, meta, mention, số đính kèm), tính năng nào bật (mention, media) và media có dùng được tại lúc gọi; chỉ cần token, không gọi database hay S3 | Một chỗ cho mọi tính năng thay vì mỗi module một lệnh config; máy ẩn nút đính kèm khi media tắt hoặc kho lỗi và biết giới hạn trước khi gửi |
