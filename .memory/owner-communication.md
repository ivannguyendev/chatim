How the owner wants design discussions and owner-facing documents:

1. **Requirements first.** Agree a requirements table row by row, with doc/code citations, before proposing options. Check each option against it, and against an independent reviewer for architecture. Show the root cause; never patch a design whose root is wrong.
2. **Plain words with an example.** Explain the flow and its consequence with a concrete case ("Lan replies to message 40…") before asking. No A/B questions full of jargon, no short field names without meaning.
3. **Ask only what changes the design.** Decide technical details myself and present them for critique. Never re-ask an answered question. Keep phases separate (own context, decisions, tasks, branch).
4. **Rewrite, don't patch.** After a review round, rewrite the summary from the final decisions. Appending a fix per question made the M2c summary long and full of dead decisions.
5. **Risks are only real consequences of this plan.** Not other systems' operations (e.g. "a user id could be reissued" is the auth system's job), and not mechanisms already accepted (e.g. the 15-minute Redis dedupe).
6. **No self-imposed limits.** No caps without a use case or an existing requirement; the owner calls a core that caps everything "cùi bắp".
7. **Flag anything that serialises work** (dense numbering, global locks); the owner rejects it by default. Prefer standard, simple mechanisms over clever protocols ("nhiều thiết kế lạ" was rejected in M2b.4).
8. **Explain with the data, step by step, no invented terms.** For a read/query design, walk through it with sample rows of the real tables (`members`, `rooms`, `mentions`) and say which table answers which question. Never coin words like "thẻ", "ngăn", "luồng". Keep "problems of the current code" visibly separate from "the fix"; when both appear in one message the owner reads the fix as having the problems and goes looking for another design (ListMentions, 2026-10-11).
9. **Scope and boundary first; decide mechanisms myself** (2026-10-12). Open with what the milestone delivers and its scope/boundary table (in scope → which service; out → where it belongs). Never ask the owner about mechanism details (sync token shape, cache keys, even reworking an old technical decision like D74); decide and present them in the summary for critique. Core is a data API + events, one call per screen. Since 2026-10-13 the owner puts the sorted conversation list and R17 unread in core (computed at read time; clients call core through websocket, not the separate app); stored per-viewer state and sync stay out. No general "boundary rule" section: the boundary is found in each phase's scope. Classify each scope row by **whose data it is**, never by who calls it: an API that reads/writes core collections (`rooms`, `members`, `messages`, e.g. `GetRooms`, `GetLastMessages`, the unread flag on a message) is core even if only Mention App calls it; only the logic that combines it (ordering, unread counting, sync, cache) is the app. On 2026-10-12 I moved those APIs to Mention App by consumer and the owner asked for the root cause. This is my judgment, not a written rule: the owner refused to add it to the CLAUDE.md checklist as too rigid.
10. **Short summaries, mechanisms by example** (2026-10-21). The owner called the M4 part 2 summary "dài lê thê, phức tạp" and understood the same mechanism at once when told as a small story (ws-2 gets 1002 then 1500, so it asks for 1003–1499 back). Owner summaries stay around 130 lines: what the part does as an example, short tables, each mechanism as a story with real numbers, then decisions/risks/tests in a few lines. Config tables, thresholds and edge cases go in the execution plan, not the summary.
11. **Start a milestone with a walk-through** (M4, 2026-10-20). The owner cut off detailed questions with "tôi còn chưa hiểu M4 làm gì": first tell what the milestone does as a story (Lan opens the app, Bình sends a message…), then ask.
12. **Rejected options get the concrete failure with numbers** (2026-10-24): the owner asked "cơ chế gây lỗi gì" when I only wrote "needs coordination". In diagrams keep core events visibly separate from app-only traffic (the owner read one shared NATS arrow as "presence comes from core").
13. **Never fold a decision that belongs to another app** (e.g. D104's distribution app) into a design without asking the owner explicitly.

**Why:** M2b pts session (2026-10-03): four patches in a row failed review until we went back to requirements. M2b.3/M2b.4 plans hid unapproved choices. M3 brainstorm (2026-10-12): three rounds of detail questions (rooms per user, MarkRead/s, sync token) got "lại khó hiểu" and "đang tính làm gì vậy"; the M3 draft mixed sync/unread into core and the owner called it patchy. M2c (2026-10-10): the owner had to remind me of rules already in memory, read risk rows they called "vớ vẩn", and asked me to rewrite the patched summary.

**How to apply:** before sending any brainstorm or summary, check it against the Design checklist in `CLAUDE.md` and this list. Related: [[design-principles]], [[workflow-pipeline]].
