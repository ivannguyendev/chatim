The rules live in the "Design checklist" of `CLAUDE.md`; this note keeps the reasons and history.

- **Data classes, not patches** (2026-10-04/05). The owner paused M2b after a plan added one fix per feature ("vá hết lỗi này đến lỗi kia"). Two external review rounds produced the data-class framework (design §4): each class has one write, one event and one repair path.
- **State-driven events; the effect engine is gone** (owner 2026-10-15, M3.1, D141–D160). The M2b.1 engine (CDC reader, `CHATIM_WORK` effects, `RECONCILE_DELAY`, Redis ack marks) was dropped as too complex and hard for developers to control. Now every write sets a `_state` bit + `_state_at` on its doc, publishes inline after the ack, clears the bit after the PubAck; the slot 0 sweeper republishes leftovers from a keyset checkpoint; projections consume `CHATIM_EVT`. Owner bar (2026-10-16): the replacement must be ≥ the old engine on the same-machine 2K bench (±10% noise); it passed. Never propose bringing back or patching the engine, a registry or delay policies; a new data kind gets a bit, a `StateTargetsOf` case and a sweep rebuilder. The owner values readable, controllable code even when it costs an extra write per message.
- **Survival timer ("phiếu hẹn sinh tồn", D111, D152)** is the standard for any derived value written inline (counter, projection, summary). Propose it directly. Steps: arm a NATS scheduled repair (`timer.arm.…` on `CHATIM_TIMER`) before the main write (arm failure → `ErrRetryLater`, nothing written); main write, then dependent write (`$inc`); disarm after. When it fires, the `timer-due` consumer recomputes; if wrong, it arms **another** timer before writing, then CASes on the version (lost CAS → Nak); no re-read after the write. Delay must exceed `CORE_REQUEST_DEADLINE`. Repairs count in `counter_repaired_total`. Rejected before it in M2b.4: Redis member set, recount worker on every change, `$inc` inside a transaction, Redis "expected value", dirty flag. In M2c the owner extended it to every count on a message (`rx`, `rc`) instead of recount-per-change (D90).
- **No internal retries — absolute** (2026-10-07, made absolute 2026-10-10): our code never retries an operation itself, not even "harmless" idempotent ones (resending the same seq after an `Unknown` insert, requeuing `ErrNotSent`, re-reading until a duplicate shows up). Fail fast with `ErrRetryLater`; the client retries. Allowed: retries built into a library/infra we use (Mongo driver retryable writes/reconnect, JetStream redelivery via Nak, nats.go publish retries). Transactions run once, never `WithTransaction`. Never offer keeping an internal retry as an option; the owner sees bounded loops as hidden complexity.
- **No data limits without a use case** (2026-10-10). Only A6 (≤ 50 mention targets) remains from M2c; bookmarks and `ListMentions` groups/rooms are unlimited.
- **Publish every change; recipients decided later** (2026-10-07). Every change publishes inline and the sweeper republishes what was lost. Subjects by data kind: `room`, `member`, `message` (plus `mention`). Core has no per-user subject and never picks recipients.
- **Mentions are stored per target** (user, group, `@all`), never expanded into users; whoever handles a mention expands it. Flat message × user rows were rejected (`@all` in a 200K room). `@here` dropped.
- **MongoDB replica set, shard-ready by config only.** The team does not run sharded clusters; growth goes to vertical scaling, zstd, retention. Code must stay shardable: room-prefixed `_id`, room prefix on every `messages` query, uniqueness only via `_id` (claim docs like `room_dms`), no `$lookup` on large collections. See [[no-sharding-in-core]].
- **Field names** (2026-10-07): the owner could not read `ro`, `ja`, `cb`, `rs`, `mc`, `n`; hence full English names except `messages` (kept short for RAM), `_ver` counters, `updated_at/by`, `request_id`, `cleared_at` as server time.

- **Self-expiring state each node owns** (M4 part 4, 2026-10-24, D200): never trade Redis writes for cross-node coordination. A node-lease presence design with shared per-user records and peers cleaning dead nodes had 12 stuck-state bugs; the owner's own answer was a TTL key per user stamped by its node.
