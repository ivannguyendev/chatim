## Hard rules

- **Never run `go` on the host.** All Go runs in `golang:1.26.9` (pinned in the Makefile and Dockerfile) through `make`. The host has Go 1.25, and nats.go v1.54 needs 1.26.
- **No comments in code.** This covers Go (including package and doc comments), tests, YAML, shell, the Makefile and `.env.example`. Names carry the meaning. Constraints that need explaining go in the design doc, plan prose or commit bodies. Generated `pkg/pb` is exempt.
- Keep code files under 200 lines, and keep `make fmt-check` clean.
- Use TDD for logic packages: `pkg/*`, `apps/*`, `tools/internal/*` and `tools/poc/internal/*`. PoC binaries in `tools/poc/<tool>` have no unit tests; run them to check them.
- Use Conventional Commits (`feat`, `fix`, `refactor`, `perf`, `test`, `docs`; never `ref`) with no AI mentions.
- Never commit `.env`, `bin/`, `rooms*.txt` or `real-texts*.txt` (the last holds real customer data). Never print values from `.env`.
- When a plan step gives a result different from its "Expected", stop and report. Don't patch it until it passes.

## Design checklist

Check every brainstorm, summary and plan against this list before showing it to the owner.
- Open every milestone plan with a scope and boundary table: what is in scope and which service owns it, what is out and where it belongs. Core offers data APIs and events, one call per screen; values per viewer computed at read time (unread, sorted conversation list) are core since 2026-10-13; stored per-viewer state and sync belong to an app.
- Map each feature to a data class of design §4 (one write, event and repair path per class). Never design a per-feature patch; a feature that fits no class needs a new class first.
- A derived value written inline (counter, projection, summary) is a direct write or `$inc` wrapped in the survival timer (design §7.1, D111); repair = recount + CAS on the version. Never recount on every change.
- No internal retries: a CAS, duplicate-key or transaction conflict returns `ErrRetryLater` (`UNAVAILABLE`) at once; consumers Nak; a failed publish leaves the `_state` flag for the sweeper; transactions run one attempt.
- No data limit without a use case or an existing requirement (A6). A page size is pagination, not a limit.
- Every change sets its `_state` bit in the same write, publishes its event inline and clears the bit after the PubAck; the sweeper republishes what is left (a new event needs a bit, a `StateTargetOf` case and a sweep rebuilder); subjects follow the data kind (`room`/`member`/`message`); core never picks recipients and never expands mention groups.
- Shard-ready: room-prefixed clustered `_id`; no secondary index on `messages` except the partial `state_pending` index (D148); uniqueness only through `_id` (claim docs such as `room_dms`), never a unique secondary index; no transaction except D100.
- Field names: full basic English words except `messages`; counters end in `_ver`; `updated_at`/`updated_by`; `request_id`.
- Owner summaries: Vietnamese, plain words with examples, written from the final state (rewrite after a review round, never append patches). Risks list only real consequences of this plan, not other systems' operations and not mechanisms already accepted.
- Ask the owner only pivotal questions, in plain words with an example; never re-ask an answered one.

## Verification and review budget

The user finds long review and test loops too slow. Run the cheapest check that proves the change, and escalate only for the area that changed.

| When | Run |
|---|---|
| While coding | `make -s go ARGS="test -race -shuffle=on ./<touched pkgs>/..."` |
| Before each commit | `make fmt-check`, `make vet`, `make lint`, and the tests of touched packages |
| New goroutines, channels or locks | add `-count=5` on that package only |
| `apps/core/internal/platform/slot` or `pkg/slotmap` changed | R5 once at the end of the task: `make go ARGS="test -race -count=20 -timeout 20m ./apps/core/internal/platform/slot/"` (~9 min) |
| Mongo/Redis/NATS adapters or `apps/core` wiring changed | `make itest` once (needs `make infra-up`) |
| Milestone end only | `make test`, `make itest`, `make core-up && make e2e`, corebench |
| Perf milestones only | before/after sweep with `scripts/bench-cell.sh NAME RATE reset [pprof]` at 1K and 5K msg/s (results in `bin/bench/NAME/`). The dev MacBook throttles on heat around 5K and other host load skews latency: record `CPU_Speed_Limit` and corebench pacer lag, and trust only CPU and Redis command counts from a cell where either is off |

- **Risky tasks get one reviewer.** These are the write path, dedupe, publish, slots and lifecycle.
  - The reviewer checks spec and quality in a single pass over the diff.
  - It does not re-run suites the implementer already ran green; at most `-count=3` on touched packages.
- **Findings:**
  - Fix Critical and Important findings in one follow-up commit.
  - Re-review only after a Critical fix, and only that diff.
  - Write Minor findings into the plan or docs instead of starting another loop.
- **Low-risk tasks** (docs, config, compose, CLI, PoC tools) get one quick check by the controller and no reviewer subagent.
- No mutation-testing passes, repeated stress runs or benchmark re-runs unless asked.
- When task N and task N+1 touch different files, review task N while task N+1 is being implemented.
- Report in a few lines. If nothing changed since the last green run, don't re-run the whole repo at the end.

## Architecture

There is one module, `github.com/ivannguyendev/chatim`, and one Dockerfile (`deploy/docker/Dockerfile`, `ARG TARGET`).
- Each app lives in `apps/<app>/` with `main.go` and `internal/`.
- `apps/core/main.go` only calls `app.Main`; wiring lives in `apps/core/internal/app`, whole-core integration tests in `apps/core/itest` (they start cores with `app.Run`). Packages are grouped by flow (design §13, names follow design §6.2/§6.3): `api/` (grpcsrv, view), `model/` (domain, pbconv, access), `send/` (actor, dedupe, flush, memberwatch), `change/` (mutate, ownership, pinproj), `event/` (publish, stateclear, projection, sweep, timer, eventkit, resync), `store/`, `platform/` (slot, metrics, redisguard, testlog), plus `config/`. Package names stay short (`actor`, not `sendactor`); a new package goes into the group of its flow.
- `pkg/` holds shared code and no business logic.
- `tools/` holds `corecli`, `corebench` and `tools/internal/route`, a slot-routed gRPC client whose retries keep the same cid.
- Communication is one-way: websocket → core over gRPC unary, core → JetStream, websocket ← NATS.

**Key encoding (`pkg/keys`).** Big-endian uint64 fields are concatenated, so byte order matches numeric order:
- messages `_id` = `room│thread_root│seq` (24B)
- message_edits = the same plus a uint32 version (28B)
- message_interactions = the message key, a kind byte (1 reaction, 2 bookmark, 3 reply) and a part: the user bytes (1..64B) or the reply's `thread│seq` (16B). Every reply key of a message is 41B, so `keys.InteractionReplyRange` (both bounds 41B) scans one message's replies in seq order; reaction and bookmark keys vary in length, so count and list them through indexes
- mentions = the message key, a target kind byte (1 user, 2 group, 3 `@all`) and the target id (none for `@all`, 25B)
- pin_actions = `room│pin_ver` (16B)
- reply_threads = the parent message key (24B, M3)
- members = `keys.Member(room, user)`: room 8B plus the user bytes (1..64B). Mongo compares BinData by length first, so never range-scan `members` by `_id`; query by room through the `room_id` index, by user with `_id` equality or `$in`
- room_events = `room│pts` (16B), unused since M2a.1 and dropped from the design
- room_dms = the string `tenant│smaller user│larger user` (`│` is U+2502, outside the id charset; `domain.DirectKey`), also stored as `rooms.dm_key`

These are `_id`s of MongoDB clustered collections (`members` too), so any history page, including the oldest, is one range scan. `thread_root = 0` is the main timeline, seq starts at 1, and `MaxUint64` is reserved.

**Counters.**
- `seq` is a position in a timeline.
- There is no room-wide event counter (proto `pts` fields are reserved). An event id is a natural key: `{room}-{thread}-{seq}` for a new message (`pbconv.MessageEventID`); M2b changes use the target doc's version.
- Room ids (`pkg/ids`) are random non-zero 63-bit numbers, sent as decimal strings, drawn once per `CreateRoom`/`OpenDirectRoom` claim; a taken id is `UNAVAILABLE` (D117, D118).
- `pin_ver` is a room's dense pin version; `rx.v` and `rc.v` version a message's reaction summary and reply count and grow by one per `$inc` or repair; a reaction or bookmark doc's `ver` counts its changes (event id tokens `-n{ver}`, `-v{ver}`). `rx.c[].n` and `rc.n` store raw deltas and may sit at or below zero while two `$inc`s land out of order; reads drop emojis at ≤ 0 and clamp `rc` (`domain.SettleReactions`, `SettleReplies`, flag `Unsettled`), and `count_repair` rewrites them when the timer fires (D113).
- Members: `ver` (≤ MaxUint32) counts membership changes of one (room, user) doc; `read_ver` counts read position changes; `rooms.member_count_ver` counts `member_count` changes (1 at creation); `rooms.owners_ver` is bumped by every owner transaction. All only grow, with gaps; tombstones are never deleted, so event ids never repeat.

**Send path (`apps/core/internal`).**
1. `grpcsrv` reads the tenant and user from the metadata keys `x-chatim-tenant` and `x-chatim-user`; callers are trusted internal apps until mTLS. Message links are checked here before the actor (`send_links.go`): `reply_to` (thread 0 only) is one `Find` of the parent, and a missing parent asks `Admit` first so a non-member never learns which seqs exist; `forward_from` goes through `forward.go` (4 key reads, D116); a message without links costs no read. `Router.Send` normalizes mentions (`ValidateMentions` against `MENTION_TARGETS_MAX`) and the actor asks `mention_all` after `send_message` for `@all`. Handlers return domain or `apperr` errors, and `pkg/grpcserver` maps them to gRPC codes at one boundary, so clients see sentinel text only.
2. `actor.Router` runs one goroutine per room, with a bounded mailbox and idle eviction. An actor is retired when its slot moves, and it keeps one write group in flight.
3. `dedupe` checks the cid against a RAM LRU, then the dedupe Redis `chatim:cid:{room}:{user}:{cid}` (pending `p:{core}` for 10s, committed for 15m). Actors call `dedupe.Batcher` (D58), sharded by `slot % CID_BATCH_SHARDS`: a Reserve blocks its caller, goes out at once when no round is in flight and otherwise joins the next round (one `EVALSHA`, at most `CID_BATCH_MAX_KEYS` keys); Commit and Abort only enqueue and a per-shard settle loop pipelines them. On Redis errors it falls back to the LRU only, using the `redisguard` cooldown.
4. `flush.Flusher` shards batch groups into `insertMany(ordered:false, w:majority)` every 2ms or 256 docs. A group that can't finish by its deadline is not sent (`ErrNotSent`); the actor fails its entries with `ErrRetryLater` at once and Aborts their cids (nothing was written).
5. Each insert ends as Inserted, Duplicate, Unknown or Rejected. Every entry is written once: the actor never resends or requeues (owner 2026-10-10: our code never retries, not even idempotent operations; driver, go-redis and nats.go retries stay). Duplicate and Unknown get exactly one `Find` (majority read) by key, with its own 1s budget detached from the group context (`reservationMargin`). Our doc (same from, cid) = written. Another core's doc at our seq (seq contention, D119): that entry and every uncommitted entry of the group fail with `ErrRetryLater` at once (committed ones still ack), and the actor yields the room once through `requestRetire` (under `r.mu`) → `a.retire`. Not found or `Find` failed = uncertain: `ErrRetryLater` (`errUnconfirmed`) at once, the cid stays pending (`p:{core}`, never Aborted), the actor is marked dirty and remembers the write by (user, cid) for `ReservationTTL` (`ambiguous_writes.go`). Rejected fails with a release. A client resend with the same cid does one `Find` of the remembered seq (1s budget): our doc → the original ack plus the cid Commit; the seq taken by another writer → Abort and `errCIDUnsettled`, so the next resend writes anew; absent or failed → `errCIDUnsettled`, still remembered. A reload driven by other traffic therefore never hides a late-landing write. An actor that lost its memory (evicted) reloads `Last` and the seed page; until the doc is visible the resend gets `PendingHere` → `errCIDUnsettled` (dirty again) until the doc shows or `CID_PENDING_TTL` expires. A single attempt fits in the reservation (`CID_PENDING_TTL` > group deadline + 1s).
6. After commit: ack (the LRU first), then the event to `publish.Publisher`, then the dedupe Commit (`c:{seq}:{ms}`) queued on the batcher (D59). A core dying between ack and Commit leaves the pending key until `CID_PENDING_TTL`; a fast retry after a failed write can see `PendingHere` and get `ErrRetryLater`. The publisher sends to stream `CHATIM_EVT` on subject `evt.{t}.message.{rid}.msg_created` with `Nats-Msg-Id` = the natural event id. Subjects go by data kind (D108, `publish.subjectFor`): `evt.{t}.room.{rid}.{kind}` (`room_created`, `msg_pinned`/`msg_unpinned`, `member_count_changed`), `evt.{t}.member.{rid}.{kind}` (`member_*`, `read_updated`, `message_hidden`, `history_cleared`), `evt.{t}.message.{rid}.{kind}` (`msg_*`, `reaction_changed`, `counts_changed`); an unknown kind is not published. One RePublish rule `evt.*.*.*.*` → `live.{t}.{kind of data}.{rid}.evt.{kind}`; everything of a room is `live.{t}.*.{rid}.>`. Core has no user subject and never picks recipients; a later distribution app does. The publisher keeps only a queue per shard (sharded by slot), so Enqueue never blocks and a room's events keep arrival order; each shard calls `PublishMsgAsync` without waiting for acks. nats.go owns the in-flight limit (`PUB_MAX_PENDING`), ack timeouts (`PUB_ACK_TIMEOUT`) and no-leader retries; failures go to `WithPublishAsyncErrHandler` and are only logged, at most once per second (D50). The message doc was inserted with `_state` bit 1 (`msg_created` pending, D142). With `publish.WithStateClears`, one ack follower per shard (`ack_followers.go`, 4096 entries, in arrival order) waits for each `PubAck` and hands the event's target (`publish.StateTargetOf`: collection, key, bit, version) to `event/stateclear`; a full follower queue only counts `publish_state_track_full_total`. Delivery is at least once: an event lost on nack, ack timeout, too many in flight, queue full or crash keeps its flag, and the sweeper republishes it from the current doc after `SWEEP_MIN_AGE` (D141–D147); the stream drops the copy by `Nats-Msg-Id` within `EVT_STREAM_DUPLICATES`.

System messages (M3, D132): `grpcsrv` checks `meta` ≤ 8KB, `kind` `text`/`system` and refuses links or mentions on `system` before the actor (`INVALID_ARGUMENT`); the actor always checks the tenant, skips membership and the member cache for `system` and asks `send_system_message` with an empty `Member` and `Request.Kind`; `messages.k = 2`, `nu` (only when true), `m`; a forward keeps the request's `skip_unread`/`meta`.

`GetHistory` reads the store directly, not through actors, and adds `reply_preview` (0 or 1 keyed `Find` per page); so do `GetReplies`, `ListBookmarks`, `ListMentions` and the M3 reads (`AROUND`: `ceil(limit/2)` back incl. the seq, two scans in parallel; `GetMessages` 1..100 seqs with `view.Default()`; `ListThreads`, `ListPins` and the message check of `GetReactions` use only `MaskDeleted` + `HideForViewer`; `my_reaction`/`bookmarked` only on `GetHistory`/`GetMessages`/`GetReplies`; every new cursor is base64url; store errors map to `UNAVAILABLE`). `GetReplies` and `ListBookmarks` page with `domain.PageLimit` (0 → 50, max 100); `ListMentions` pages at 20 (0 → 20, more = `INVALID_ARGUMENT`).

**Two Redis instances (D44, D45).**
- State, `chatim-redis`: used only by the slot manager: `chatim:core:*`, `chatim:cores`, `chatim:slot:*`, pub/sub `chatim:slots:changed`. AOF everysec, `noeviction`.
- Dedupe, `chatim-redis-dedupe`: `chatim:cid:*`, `chatim:req:{room}:{user}:{request_id}` (`AddMembers` retries, same Lua and batcher, D99), `chatim:req:create:{tenant}:{user}:{request_id}` (`CreateRoom`, D118). Since M3.1 there are no acked-event marks (`chatim:evtack:*` is gone; pending events live in `_state` on the docs). No persistence, `REDIS_DEDUPE_MAXMEMORY` (512mb), `allkeys-lru`. If it dies, dedupe falls back to the LRU; events do not depend on it.
- Both require AUTH. Passwords come from `.env` through compose secrets; cores read `REDIS_PASSWORD_FILE`/`REDIS_DEDUPE_PASSWORD_FILE`, tools read `-redis-password` or `REDIS_PASSWORD`. Passwords never go in argv, `docker inspect`, echoed make lines or logs.

- Dedupe client (D60): `PoolSize` = `MaxActiveConns` = `2 × CID_BATCH_SHARDS + 4`, `MinIdleConns` = `2 × CID_BATCH_SHARDS`, `MaxRetries -1` (Reserve is not idempotent), `DialerRetries 1`. Both clients set `DisableIdentity`; the state client keeps its pool of 4 and default retries (changing it touches leases and needs R5). go-redis still drops a connection after a timeout; reusing it could read a late reply.

**Mongo credentials (D46).** Compose secret `mongo_password` comes from `MONGO_ROOT_PASSWORD`. Cores get a credential-free `MONGO_URI` plus `MONGO_USER` and `MONGO_PASSWORD_FILE` (`MONGO_AUTH_SOURCE` defaults to `admin`). A `MONGO_URI` with credentials still works (itest, non-compose runs), but not together with `MONGO_USER`. mongosh never gets `-p`: scripts authenticate inside `--eval` with `db.getSiblingDB("admin").auth(user, require("fs").readFileSync("/run/secrets/mongo_password", "utf8").trim())`.

**Slots and soft ownership.** `slot = mix64(room) % 1024` (`pkg/slotmap`, with rendezvous `Score` and `Preferred`). `slot.Manager.Step` runs once per tick:
1. Heartbeat with one Lua script: `SET chatim:core:{id}`, `ZADD chatim:cores` scored by Redis `TIME`, and a prune of expired cores.
2. Renew the leases `chatim:slot:{n}`. This is a multi-key Lua script, so Redis must be a single primary, not Redis Cluster.
3. Claim or release slots toward `ceil(1024/alive)`.
4. Publish on `chatim:slots:changed`.

Hooks:
- The hooks receive batches of slots and share one `HookTimeout` per Step.
- BeforeRelease and AfterLose call `Router.EvictSlots`.
- AfterClaim calls `EvictSlots` only.

Rules:
- `Owns()` is true only while the lease stamp is newer than `min(LeaseTTL, HeartbeatTTL) − Tick`, measured from the start of the tick (D24).
- The slot manager uses its own Redis client.
- Never use `SCAN` or `KEYS`: cid keys fill the keyspace.
- Clients use `slotmap.Resolver` to map a slot to a core address.

**Invariant: any core must handle any room correctly.** Ownership only buys batching, ordering and cache hits. Correctness comes from the unique `_id` acting as CAS, so a Redis failover or a double owner never loses or duplicates a message.

**State-driven events (`event/publish`, `stateclear`, `sweep`, `projection`, `timer`, `eventkit`, `resync`; M3.1, D141–D159; replaces the effect engine of D52, D65, D66, D79–D81 and the reader/worker parts of D83, D84, D91, D103, D109).**
- Pending bits (D142–D145, D149): every store write sets its bit in `_state` (int32 bitmask) and `_state_at` (`$min`, the oldest pending bit; inserts use the doc time, updates server `$$NOW` through update pipelines) in the same write; no extra write before the ack. Bits (`store.StateBit`): `messages` 1 `msg_created`, 2 `counts_changed` reactions (`rx.v`), 4 `counts_changed` replies (`rc.v`); `message_edits` 1 (facts `ver ≥ 1`; the `ver 0` row has none); `message_interactions` 1 (`reaction_changed`/`bookmark_changed` at `ver`; a byte-identical same-emoji or same-state upsert sets nothing; reply docs none); `pin_actions` 1; `members` 1 `member_*` (`ver`), 2 `read_updated` (`read_ver`), 4 `history_cleared` (`cleared_at`), 8 `room_preferences_changed` (`preference_ver`); `hidden` 1 (first hide only); `rooms` 1 `room_created`, 2 `member_count_changed` (`member_count_ver`), 4 `room_updated` (`info_ver`). The owner transaction (D100) writes its bits inside the transaction. `mentions`, `reply_threads`, `room_dms` and reply docs carry none. Each of the 7 collections has the partial index `state_pending {_state_at: 1, _id: 1}` where `_state` exists (D148). Ports: `store.EventStates` (`Pending` keyset page by `(_state_at, _id)` in `[from, before)`, at most `store.MaxPendingPage` 1000; `Clear` and `Mark`, both version-conditional for versioned bits, grouped per collection and bit with no target cap, runs of consecutive insert-once keys become one range `UpdateMany` and the rest point writes, then chunked into `BulkWrite`s of ≤ 500 statements so no run is split; a target that fails `StateTarget.Validate` rejects the call) and `store.SweepCheckpoints` (`sweeper_state`, one doc per collection, `w:majority`, forward only). A bit clear drops both fields once no bit is left. Writes made outside core (mongosh, migrations) must set `_state` + `_state_at` themselves, or no event is published.
- Publish and clear (D144): a command writes, acks, then enqueues its event; `publish.WithStateClears` runs one ack follower per shard that waits for each PubAck and adds `publish.StateTargetOf(event)` (19 kinds; reactions use the doc `ver`, pins `Seq` = `pin_ver`, `counts_changed` by counter) to the `stateclear.Queue`. The queue never blocks: `Add` drops when full (`STATE_CLEAR_QUEUE` 65536) and counts it; it flushes `STATE_CLEAR_FLUSH` (2s) after the first target or at `STATE_CLEAR_BATCH` (16384) targets, so a room's consecutive acked seqs of one flush become one range write; each flush has `STATE_CLEAR_TIMEOUT` (5s); a refused flush is counted; it drains within 1s at stop. Anything not cleared is republished by the sweeper and dropped by the stream as a duplicate. Events the projections or timers publish (`counts_changed` replies, `member_count_changed` after a repair, D153) follow the same pattern. `CreateRoom`/`OpenDirectRoom` publish `room_created` (with the settled count), one `member_added` per member and `member_count_changed` `{room}-members-v1` inline.
- Sweeper (`event/sweep`, D146, D147, D154, D158): runs only on the slot 0 owner (`Owns(0)`, log `event sweeper started`), every `SWEEP_INTERVAL` (2s). Per collection: read the checkpoint, page `Pending` (`SWEEP_BATCH` 500) over `[checkpoint − SWEEP_LOOKBACK (60s), now − SWEEP_MIN_AGE (15s))`, no cursor kept between pages; the first pass of each lead scans from the start of the index. Per doc and bit it rebuilds the event from the current doc (`rebuild_*.go`: messages, rooms, edits rerun `ApplyEdit` + `PurgeText` first and keep the flag while the projection is behind, interactions, pins run `pinproj.Project` then publish the fold, members, hidden), publishes it on its own JetStream client `sweepJS` (≤ `2 × SWEEP_BATCH` in flight, `SWEEP_RATE` 5,000 events/s, burst `min(Batch, Rate)`), waits for the PubAck and `Clear`s the bit. A publish failure or a lost pin CAS keeps the flag; the checkpoint moves only forward, to the oldest failure or to `now − SWEEP_MIN_AGE`. After each collection's pass one probe `Pending(0, window start, 1)` looks for flags older than the window (a bit raised later with an old `_state_at`); a hit makes the next pass scan from the start and logs `pending state older than the sweep checkpoint`. A gone doc is dropped and cleared with the version read; a gone doc whose versioned bit has no known version keeps its flag (counted as a failure); a doc with only unknown bits is warned once per key. Two cores holding slot 0 during a handover may both publish; the stream drops the copy.
- Projections (`event/projection`, D150, D159, D160): one durable pull consumer `projections` on `CHATIM_EVT` (filter the single subject `evt.>`, explicit ack, `AckWait` 30s, `MaxAckPending` 4 × `PROJECTION_FETCH_BATCH`, `DeliverAll`); `EnsureConsumer` creates it at boot and deletes the old durables `projection-room_activity`, `projection-mention_reply_index`, `projection-mention_read` (not-found ignored). Only the slot 0 owner fetches it (`projection.WithLeader`, checked every `SLOT_TICK`), `PROJECTION_FETCH_BATCH` 1024 / `PROJECTION_FETCH_WAIT` 1s through `eventkit.PullSource` (`FetchMaxWait`: the server expires the pull and the client waits for that signal, so delivered messages are not dropped at the deadline). Each batch is decoded once and each handler (`Projection.Keeps` + `Handle`) gets the subset it keeps, the three running in parallel; kinds no handler keeps are only acked. Settle (`consumer_settle.go`) per message: OK → `Ack`; `eventkit.Gone` → `Ack` and counted as dropped; undecodable → `Term`, dropped; any other error → `Nak(eventkit.NakDelay(NumDelivered))`, so a failing event delays only itself. Losing the lead finishes and settles the batch in hand and `Nak(0)`s a batch fetched after the loss; at stop `PullSource.Fetch` reads the pull in flight to its server expiry (≤ 1s; the timer consumer too, 500ms) and the consumer `Nak(0)`s what it brought, so a stop drops no delivery. Metrics carry `projection="projections"`. Handlers: `room_activity` keeps 13 kinds and writes one `TouchActivity` row per (room, thread) per batch (max seq, newest message time, edited flag): `$max last_seq`/`last_message_at` from `msg_created`, and `last_change_at`, `activity_bucket`, `last_edit_at` (edit/delete on thread 0) stamped with server `$$NOW` (`$max`). `mention_reply_index` takes `msg_created`/`msg_edited`/`msg_deleted` and reads `reply_to` and mentions from the event (no `Find`): a reply arms a `replies` count timer → `AddReply` → only a new doc `$inc rc +1` (bit 4) → `counts_changed` → disarm; a deleted reply `RemoveReply` and `rc −1` the same way; mentions by `store.PlanMentions` + `ApplyMentions` when the event's `message_ver` ≥ the doc's, then `RaiseSharedMention` for `@all`/groups; every live reply `ReplyThreads.Touch`es `reply_threads` (D130). `mention_read` takes `read_updated`: one `MembersOf` per room per batch, a `read_ver` behind the event Naks, a missing member is dropped, else `Mentions.MarkRead(room, user, current read_seq)`. Failure ladder 5s/30s/2m/10m is fixed (`eventkit.NakDelay`); deliveries ≥ 6 count in `projection_stuck_total`.
- Consumer contract (D156; for websocket M4, Mention App and any consumer): delivery is at least once and a sweeper republish can arrive after newer events. Dedupe by event id and by the doc version (`ver`, `read_ver`, `pin_ver`, `info_ver`, `preference_ver`, `rx.v`/`rc.v`, `member_count_ver`; larger wins). For `msg_created`, drop an exact seq already seen and call `GetHistory` on a gap (seq > last + 1); never "drop if seq ≤ last seen". Only the last state of a set or counter doc is guaranteed.
- Survival timers (`event/timer`, D111, D152): stream `CHATIM_TIMER` (`TIMER_STREAM`, WorkQueue, `AllowMsgSchedules`, `MaxAge` 2h, duplicates 2m). `ArmMemberCountCheck(room)` publishes to `timer.arm.{room}.{op}` and `ArmMessageCountCheck(key, counter)` (thread 0, `reactions` or `replies`) to `timer.arm.{room}.{thread}.{seq}.{counter}.{op}` with `WithScheduleAt(now + delay)` and target `timer.due`, a 29-byte payload, `op` a fresh random uint32; it waits for the PubAck. `Disarm` is `DeleteMsg` by the PubAck seq (already fired = `ErrMsgNotFound`, not a warning). One shared durable consumer `timer-due` (fetch 64 / 500ms, `AckWait` 30s) runs `count_repair` (recount, equal and settled = republish only, else arm a new timer then CAS `rx.v`/`rc.v` with the bit) and `member_count_repair` (CAS `member_count_ver` with bit 2), then publishes; gone = ack + drop, failure = Nak on the ladder. Delays `MEMBER_COUNT_CHECK_DELAY` and `MESSAGE_COUNT_CHECK_DELAY` (5s, both > `CORE_REQUEST_DEADLINE`); firing rounds up to the second.
- Boot rules: `SWEEP_MIN_AGE > PUB_ACK_TIMEOUT + STATE_CLEAR_FLUSH + STATE_CLEAR_TIMEOUT` (2s + 2s + 5s < 15s), `SWEEP_MIN_AGE + SWEEP_INTERVAL < EVT_STREAM_DUPLICATES`, `SWEEP_LOOKBACK > CORE_REQUEST_DEADLINE + 10s` and `> SWEEP_MIN_AGE + 10s`, `SWEEP_BATCH ≤ 1000`, `PROJECTION_FETCH_BATCH` ≤ 8192 and `PROJECTION_FETCH_WAIT` ≤ 1s (a fetch in flight at stop ends within the 1s projections stop phase); old `PROJECTION_ACTIVITY_FETCH_*` are ignored, `TIMER_STREAM`/`TIMER_SUBJECT_ROOT` differ from the event stream. Old `RECONCILE_*`, `WORK_*`, `EVT_ACK_MARK_TTL` env vars are ignored.
- Resync (`event/resync`, D155): `/app resync` picks rooms by `activity_bucket >= hour(from)` or `created_at` in range (or `-room`), reads the current docs in the range and re-flags them with `EventStates.Mark` (pages ≤ 200 per collection, `-rate` targets/s; a pending doc keeps its old `_state_at`, else now; a gone or changed doc is skipped): `rooms` bit 1 if created in range, 2 if `member_count_ver ≥ 1`, 4 if `info_ver ≥ 2` and updated in range; main-timeline messages bit 1; edit facts `ver ≥ 1`; current reactions and bookmarks; `pin_actions`; `members` by `last_change_at` (bit 1, plus 2/4/8 when `read_ver ≥ 1`, `cleared_at` set, `preference_ver ≥ 1`); `hidden`. It arms one count timer per message with reactions and per parent with reply docs in range. The sweeper republishes and the projections rerun (idempotent). After a `CHATIM_EVT` purge, wait out `EVT_STREAM_DUPLICATES` (5m) first or the stream drops the same ids. A room with only member/read/hide/clear/rename/preference changes in the gap needs `-room`. `-dry-run` only counts.
- Room activity (`rooms.last_seq/last_message_at/last_change_at/activity_bucket`, D69, plus `last_edit_at`, D138) is written only by the `room_activity` projection; `activity_bucket` is the hour of the last change and is indexed (`{activity_bucket: 1}`, plus `{created_at: 1}` for resync). A replayed event also raises `last_change_at`/bucket to now (accepted). In e2e the conversation list settles 0–536ms after `msg_created` (was ~5s with the engine).

**Edits (`apps/core/internal/change/mutate`; D62–D64, D82–D87, D96, D97, D109, D114, D115).**
- `EditMessage`, `DeleteMessage`, `HideMessage` and `ClearHistory` run in `mutate`, called by `grpcsrv`, not through actors; tools still route them by the room's slot.
- Edit and delete insert an immutable fact into `message_edits` (`_id` = `room│thread│seq│ver`, 28B, the CAS; `ver = base_ver + 1`; each row is one content version `{room_id, tenant, kind, created_by, text, created_at}`; the first edit also inserts-if-absent the `ver 0` row (`kind original`, the sent text, sender, sent time); a delete of a never-edited message writes no `ver 0` row), project it onto `messages` with `ApplyEdit` (only where `v < ver`), purge older fact texts on delete, then ack. A duplicate fact with the same author, kind and text (and, when mentions were sent, the same targets as a set and `@all`) is a retry and succeeds; a stale base or a deleted message is `FAILED_PRECONDITION`. `EditCmd.Mentions` nil keeps the message's mentions (copied into the fact), an empty set clears them; every fact and the `ver 0` row carry the full mention set (`mention_targets`, `mention_all`); a new `@all` asks `mention_all`. The fact carries `_state` bit 1, so a core dying between fact and projection is healed by the sweeper, which reruns `ApplyEdit` (and the text purge on delete) before it publishes (D151); the stream drops the duplicate event by id.

**Reactions, bookmarks, replies, mentions and pins (`mutate`, `pinproj`, `grpcsrv`, `mention_reply_index`; D88–D95, D112–D116, D119).**
- `ReactMessage`, `SetBookmark`, `PinMessage` and `UnpinMessage` run in `mutate` (`Admit` → `Find` → `Allow` with actions `react_message`, `set_bookmark`, `pin_message`, `unpin_message`; the default policy allows any member and `MESSAGE_LOCKED_KINDS` does not apply, D94).
- Interactions live in clustered `message_interactions` (D112; fields `message_key room_id tenant kind actor_id value previous_value reply_seq state ver created_at updated_at`, `kind` stored as a string; indexes `{message_key, kind, state, value}` (recounts, live replies), `{tenant, actor_id, kind, state, updated_at: -1, message_key: -1}` (`ListBookmarks`), `{room_id, kind, updated_at}` (resync)). A reaction is one emoji per (user, message) in `value`. Set is one `FindOneAndUpdate({_id}, pipeline, upsert, ReturnDocument Before)`: `$cond` keeps every field when the doc is live with the same emoji, so it stays byte-identical (no oplog entry, no feed change); otherwise `ver+1`, `previous_value` = the old emoji, `state 1`. The filter is equality on the unique `_id`, so the server retries a duplicate-key upsert itself. Remove is an update without upsert that leaves the tombstone `state 2` (keeping `value` so the count knows which emoji to drop). No cid: the command is the desired state (D89). A deleted message only accepts a removal. Bookmarks use the same upsert (`on` on a deleted message is `FAILED_PRECONDITION`, `off` always works; same state = `changed false`, no event); `ListBookmarks` keeps entries the caller can no longer see with `available = false` and no text.
- Emojis come from the fixed list `REACTION_EMOJIS` (default `👍,❤️,😂,😮,😢,🙏`, blank = default; boot checks non-empty, valid, no duplicates, at most 100). An emoji outside it is `INVALID_ARGUMENT` (`domain.ErrEmojiNotAllowed`), checked before membership and policy; the list length is the per-message limit. `GetReactionSettings` (not room-routed, needs caller metadata) returns the list in config order so the frontend shows only those (D95).
- Counts (design §7, D113): `messages.rx {c: [{e, n}], v}` (an array sorted by count then emoji) and `messages.rc {n, v}` change only by `$inc` of deltas inside a survival timer. React: validate the emoji → `Admit` → `Find` → `Allow` → `ArmMessageCountCheck(key, reactions)` (failure = `UNAVAILABLE`, nothing written) → set/remove (an error keeps the timer for the unknown outcome; no change = disarm, no event, so a repeat still costs arm + disarm) → enqueue `reaction_changed` → `AddReactionCounts` (one pipeline with `$map/$reduce/$filter/$sortArray`, `v+1`, returns the doc after; a failure is logged, keeps the timer, still acks and replies with the old summary plus the deltas, no `counts_changed`) → disarm → enqueue `counts_changed` `…-reactions-v{v}`. The reaction upsert sets `message_interactions` bit 1 and `AddReactionCounts` sets `messages` bit 2. Replies are counted by the `mention_reply_index` projection the same way (`AddReplyCount`, only when `AddReply` inserted or `RemoveReply` really flipped). Deltas are stored unclamped (see Counters). `count_repair` recounts with `CountReactions`/`CountLiveReplies` (covered, majority) and CASes `SetReactions`/`SetReplyCount` (`$exists: false` at version 0) after arming a new timer; repairs go to `counter_repaired_total{counter="reactions"|"replies"}`. No witness, no touch, no recount per change.
- Pins (D92, D119): no base version. `pinproj.Projector.Current` folds `rooms.pins/pin_ver` with the facts after it; the command appends `pin_actions {_id: room│pin_ver+1}` once (dense pv, so `PIN_LIMIT` 50 is exact; already in the wanted state = success with no fact; a duplicate key with the same op, message and user is the result, another fact = `ErrRetryLater` at once), then `Project`s once (fold + CAS `pv == p`; a lost CAS is `ErrContended`: the command answers with the local fold, the fact keeps its `_state` bit and the sweeper folds and CASes again before it publishes). Pinning a deleted message is `FAILED_PRECONDITION`; unpinning still works. `Rooms.Get` never reads pins.
- Events (D93): `reaction_changed` `{room}-{thread}-{seq}-{user}-n{n}`, `counts_changed` `{room}-{thread}-{seq}-reactions-v{v}` or `…-replies-v{v}` (`reply_count {count, ver}`), `bookmark_changed` `{room}-bm-{thread}-{seq}-{user}-v{ver}` (subject `member`), `msg_pinned`/`msg_unpinned` `{room}-p{pin_ver}` with the message snapshot (no text when deleted). Intermediate reaction and bookmark events can be lost; only the last state is guaranteed (set class). `GetHistory` returns `Message.reactions` (counts only), `reply_count` and `reply_preview`. SysMsg cids are `sys-{event_id}`.
- Replies (D114): `messages.rp {th, s}` (thread 0, same room). `reply_to` with `thread_root ≠ 0` is `INVALID_ARGUMENT`; a deleted parent can still be replied to. Reply docs (`_id` = parent key│3│`thread│seq`) are written only by `mention_reply_index`; `RemoveReply` on a missing doc writes the tombstone first so a late add never revives it. `GetReplies` = `Admit` → `Find` parent (`NOT_FOUND`) → `Allow(read_replies)` → scan `keys.InteractionReplyRange` skipping tombstones → `Find $in` → view; `next` = last reply seq, 0 = end. A parent deleted right after a new reply, before the projection built its doc, is allowed (accepted window).
- Mentions (D115): `messages.mt [{k, i}]` (≤ `MENTION_TARGETS_MAX` 50 after dedupe, id `[A-Za-z0-9_:-]{1,64}`, more than 4 × limit rejected before dedupe) and `ma` (`@all`, action `mention_all`). Clustered `mentions` (fields `message_key room_id tenant kind target thread_root seq sender_id state message_ver created_at updated_at`; `kind` `user`/`group`/`all`, `target` = `user:{id}`, `group:{id}` or `all:{room}`; `state` 1 live, 2 retired, 3 live and read (user docs only); indexes `{tenant, target, state, created_at: -1, message_key: -1}` (path A), `{room_id, kind, created_at: -1, message_key: -1}` (path B), `{room_id, target, thread_root, seq}` (`mention_read`) and `{message_key: 1}`, the last because a delete `$unset`s `mt/ma` and a key-prefix scan breaks on BinData length order). `mention_reply_index` plans with `store.PlanMentions` and writes only when the event's `message_ver` ≥ the doc's (a live state 3 stays 3, a re-added target starts at 1); a delete retires every doc; `@all`/group raises `rooms.last_shared_mention_at` (`$max`, never lowered). `ListMentions(groups[{id, since}], before, limit ≤ 20)` (`grpcsrv/mentions.go`, `mention_paths.go`, pure helpers in `store/mention_merge.go`, `mention_page.go`): `RoomsOf` once (covered by the user-rooms index), room since = `max(joined_at, cleared_at)`; path A `ListByTarget(user:{caller})` (states 1 and 3; hide tenants 1 only), dropping rooms the caller left and docs not after the since; path B only through the caller's rooms: `SharedMentionTimes` (`$in` of 1,000 rooms per chunk) → `store.SharedMentionRooms` drops rooms with nothing after their since and sorts newest first → batches of `store.SharedMentionBatch` = 200 rooms, each one `ListShared` `find` with two equality `$or` branches per room (`all`; `group` + the caller's groups, `GroupSince` pushed down when every group has a since) after the since, a `SORT_MERGE` at 200 rooms; groups in rooms the caller is not in are never read; stop early once the page is full and newer than the next room's `last_shared_mention_at` (`store.MentionsSettled`). Each source scans at most `store.MentionRounds` = 3 rounds per page; a capped source reports its end and the page keeps only items not older than the newest end, `next` pointing there (`store.PageMentions`), so a page can be short with `next` set. Merge one item per message, then per (room, thread) `Authorize(read_history)` + `Find $in` + view. Read = mention `created_at` ≤ the sent time of the message at the room `read_seq` (`MessageTimes.SentTimes`, batched, cached per call), on both paths and in threads; items are `MentionItem{message, read}`. Tenants in `MENTION_HIDE_READ_TENANTS` (comma list, bad id = boot error; until a tenant settings store in M3) hide read mentions: path B raises each since to that read time (`store.RaiseSinceToRead`), path A queries state 1 and drops read items by time; other tenants see everything with the flag. Worst case at 5,000 rooms, every room with fresh `@all`, hide tenant: 113 store queries per page (85 for mark) plus the message reads. Core never expands groups and has no `@here`.
- Forward (D116, `grpcsrv/forward.go`): with `reply_to` or a bad source = `INVALID_ARGUMENT`; `Admit(forward_message)` on the source (missing/other tenant = `NOT_FOUND`, non-member = `PERMISSION_DENIED`); missing source, cleared or hidden for the caller = `NOT_FOUND`; deleted = `FAILED_PRECONDITION`; then `Allow` with the source author and kind. The command carries the source's current text, no mentions (client text and mentions dropped) and `fw` = the source's `fw` or the source itself.
- Wiring: `apps/core/internal/app/service_wiring.go` builds `pinproj`, the message count timers and the `grpcsrv` deps (mentions, member rooms, sent times, `MENTION_HIDE_READ_TENANTS` as `HideRead`, direct rooms, request dedupe) from the Mongo store and passes `mutate.Limits` from config.

**Rooms, members, priority and read position (`grpcsrv`, `mutate`, `ownership`, `memberwatch`; D96–D111, D117, D118).**
- Room creation (`grpcsrv/room_ensure.go` `ensureRoom`, rerunnable): `ArmMemberCountCheck` (failure = `UNAVAILABLE`) → `Rooms.InsertRoom` (`member_count 0`; a duplicate of our own room goes on, another room = disarm + `UNAVAILABLE`) → `AddMembers` with `request_id {room}-created` (founders get `read_ver 1`, so their first `MarkRead` is `-v2`) → `AddMemberCount` → disarm → events. `OpenDirectRoom(other_user)` (yourself = `INVALID_ARGUMENT`, policy `open_direct`): `DirectRooms.Claim` upserts `room_dms` with `$setOnInsert` and a fresh id, so concurrent opens get one room; both members active = `{room, created false}`, else `ensureRoom` = `{room, created true}`; an id held by another room = `Repoint` CAS to a fresh id and `UNAVAILABLE`. A DM has no owner (two `member`s). `CreateRoom` is for groups/channels only (DM = `INVALID_ARGUMENT`), `request_id` required (`ValidCID`), one id draw (taken = `UNAVAILABLE`); `dedupe.Requests` on `chatim:req:create:{tenant}:{user}:{request_id}` (shard FNV(tenant:user)): busy = `UNAVAILABLE`, new = `ensureRoom` with `Finish` (room id in `Record.Seq`) right after `InsertRoom` (`Cancel` only when nothing was inserted), done = read the room and finish `ensureRoom` for founders with no member doc yet (removed founders keep their tombstone).
- `AddMembers`, `RemoveMember`, `LeaveRoom`, `ChangeMemberRole`, `SetMemberPriority`, `MarkRead`, `MarkUnread` run in `mutate` (7 RPCs, `grpcsrv/members.go`, `read.go`), routed by the room's slot. No internal retries (rule for every command, owner 2026-10-07; none left since M2c, D119; the Unknown resend dropped by the owner 2026-10-10): a CAS miss, a transaction conflict or a request in flight on another core is `ErrRetryLater` (`UNAVAILABLE`) at once; clients retry (`tools/internal/route` keeps the same `request_id`). A DM refuses member commands (`FAILED_PRECONDITION`).
- `members` doc (D98): `{_id, room_id, tenant, user_id, role, state, priority, joined_at, ver, previous_role, previous_state, previous_priority, request_id, updated_at, updated_by, last_change_at, cleared_at, read_seq, read_ver}`; `state` 1 active / 2 tombstone (never deleted); `state`, `priority`, `ver`, `read_seq`, `read_ver` always written. Indexes `{room_id, state, role, priority: -1, joined_at, user_id}` (count, owners, successors) and `{tenant, user_id, state, room_id, joined_at, cleared_at, read_seq}` (rooms of a user; covers `RoomsOf`). `rooms` adds `member_count_ver`, `owners_ver` and `last_shared_mention_at` (written only by `mention_reply_index`).
- Default policy (D101): owner does everything; admin adds people and removes `member`-role people; only the owner changes roles and sets `priority`; anyone leaves. The policy is asked before revealing whether the target exists (a missing or left target is a fake `member`). Codes: bad input or over `MEMBER_BATCH_MAX` → `INVALID_ARGUMENT`; DM, last owner demoting itself → `FAILED_PRECONDITION`; not active, denied, a never-member leaving → `PERMISSION_DENIED`; removing a never-member, changing a non-active target → `NOT_FOUND`; removing a tombstone, leaving twice, setting the current role/priority → `OK` with `changed = false`.
- Add (D99): `request_id` is required and deduped (`dedupe.Requests`, `chatim:req:*`, RAM LRU + Redis, `CID_COMMITTED_TTL`): done → reread and return the people still active and added by this request; busy → `UNAVAILABLE`; new → arm the timer → one `BulkWrite(ordered:false)` of upsert pipelines with `$cond` (an active doc stays byte-identical) → forget the actor cache → `$inc member_count` by `UpsertedCount + ModifiedCount` → disarm → `member_added` per person, then `member_count_changed`. Rejoiners always get role `member`, `priority 0`, `read_seq = max(old, last seq)`, keep `cleared_at`. Dedupe holds only 15 minutes and while Redis keeps the key.
- Plain path (target not an owner, not promoting to owner): one `UpdateOne` CAS on the target's `ver` (`ApplyMember`); remove/leave of an active doc arms the timer first and `$inc`s −1 after.
- Owner path (D100, the only transaction): `ownership.Affects` → `OwnerChanges.ChangeOwners` runs one transaction (`StartTransaction`/`CommitTransaction`, never `WithTransaction`): read `owners_ver`, the docs, up to 2 owners and the top admin/member candidates; the pure `ownership.Plan` writes the successor first (admin before member, then highest `priority`, earliest `joined_at`, lowest user id) then the target, each a CAS on `ver`; `$inc rooms.owners_ver` (the shared conflict point) and the member count in the same doc update; commit. No timer. `LeaveRoom` returns `new_owner`; `member_removed` carries none. Invariant: a group with active members always has an active owner. memstore gives the same semantics.
- Member count (D102, D111): only `Rooms.Create`, the in-command `$inc` (by docs that really changed state), the owner transaction, the `member_count_repair` timer consumer and `/app recount` change it; each sets `rooms` bit 2. A failed `$inc` is logged, the timer stays armed, the command still succeeds. Arm failure → `UNAVAILABLE` before any write. `MEMBER_COUNT_CHECK_DELAY` (5s) must exceed `CORE_REQUEST_DEADLINE`.
- Read position (D105): `MarkRead(seq)` clamps 0 or past the end to the last seq and raises when `read_seq < seq`; `MarkUnread(seq)` (0 → `INVALID_ARGUMENT`) lowers to `seq − 1`; both bump `read_ver`, use plain operators and never touch `ver`; a real move publishes one `read_updated` `{room}-rd-{user}-v{read_ver}`.
- Events (D104, subject `member`): `member_added` (with `read_seq`, `read_ver`), `member_removed` (`REMOVED`/`LEFT`), `member_role_changed`, `member_priority_changed`, all `{room}-mb-{user}-v{ver}`, derived from the doc's `previous_*` by `pbconv.MemberEvent`; `member_count_changed` `{room}-members-v{member_count_ver}` on subject `room`. Only the last state of a doc is guaranteed.
- Actor member cache (D106, D110): generation + 10s TTL; no negative caching. `Router.ForgetMembers(room)` runs after each real change on the same core; `memberwatch` on every core subscribes core NATS `{live}.*.member.*.evt.member_removed` and `….member_role_changed`, takes the room id from subject token 4 and forgets. Lost events (core NATS has no replay) fall back to the TTL.
- Config: `MEMBER_BATCH_MAX` (500, 2..1000, counted after dedupe) for `CreateRoom` and `AddMembers`; no total member cap.

**Permission hook and reader pipeline (`access`, `view`).**
- `access.Policy` is the single permission point; `access.Checker` always enforces tenant and membership first, then asks the policy. `Checker.Admit` checks tenant and membership only, `Checker.Allow` asks the policy with `Request.Author` and `Request.Kind` (the target message's author and kind, empty for room actions), `Authorize` does both; actions on one message (edit, delete, hide, edit history) run `Admit` → `Find` → `Allow`. The default policy of `NewChecker` and the actor is `access.DefaultPolicy`: edit/delete only by the author, every other action for any member (D86); the chat policy module (user → role → permission) plugs in at Phase 2.
- Locked kinds (D87): core never hard-blocks edit/delete of a message kind (e.g. future system messages). `MESSAGE_LOCKED_KINDS` is a comma-separated list of kind names, case-sensitive, empty by default (nothing locked); an unknown name is a boot error. `DefaultPolicy.LockedKinds` denies `edit_message`/`delete_message` on a locked kind even to the author. Only the mutate checker gets the config; the `grpcsrv` and actor checkers use `DefaultPolicy{}`. Today only `text` exists; a new kind adds one entry to `domain.kindNames`.
- `SendMessage` asks the checker in the actor (`actor.WithPolicy`; `mention_all` after `send_message`), `forward_message` and the reply admit in `grpcsrv`, edit/delete/hide/clear/react/bookmark/pin/unpin, member and read commands in `mutate`, `open_direct` in `grpcsrv`, `GetHistory`, `GetEditHistory`, `GetReplies` (`read_replies`), `ListBookmarks` and `ListMentions` (`read_history` per room) in `grpcsrv`. `Rooms.Member` treats a doc with `state ≠ 1` as not a member.
- M3 actions: `read_reactions`, `read_members` (any member), `update_room` (owner, admin), `send_system_message` (allowed by default; the policy gets an empty `Member`, so a future role policy must not rely on it), `set_room_preferences` (`Admit` only).
- `view.Pipeline` runs steps over a page read from the store; `view.CollapseRetried` hides CD2/CD3 duplicates by (sender, cid). `view.MaskDeleted` and `view.HideForViewer` (`CreatedAt ≤ Viewer.ClearedAt` or hidden by the reader → `hidden`) follow it in `view.Default()`; both use `domain.Message.WithoutDeletedContent` (shared with `pbconv`): deleted → no text, mentions, `@all`, forward, reactions or reply count, `rp` kept; hidden → also no `rp`. Seq and version are kept.
- On seq contention with another core's doc the actor fails the entry and every uncommitted entry of its group with `ErrRetryLater` at once and yields the room once through `a.retire` (always via `requestRetire`, which holds `r.mu`) so the next command goes to the real owner (D77, D119); no reassignment, no backoff, no resend. `room_yields_total` counts real yields only (alert `ChatimSeqContention`).

**Process lifecycle (`apps/core`).**
- Config is validated at boot by `apps/core/internal/config`, which applies cross-field timeout rules; components export `Validate()`.
- Start order: publisher → state clear queue → flusher → cid batcher → router → slot manager → timer consumer → projections → sweeper (works only while it holds slot 0) → live watchers `memberwatch` then `roomcache.Watch` (one group, subscribed once the router runs; a failed start never serves gRPC) → gRPC. gRPC is served only after a clean start. Bootstrap creates the `state_pending` indexes, `sweeper_state`, `CHATIM_TIMER` and the three projection consumers; it no longer touches `CHATIM_WORK` or `reconciler_state` (an old database may still hold `reconciler_state`; it is harmless and can be dropped by hand).
- Shutdown order: `/readyz` false → drain delay → gRPC → sweeper (1s) → projections (1s) → timer consumer (1s) → `memberwatch` and `roomcache.Watch` (Unsubscribe, instant, no stop phase) → router → cid batcher (flushes queued Commit/Abort within `2 × REDIS_OP_TIMEOUT`) → flusher → publisher (drains its queues, then waits for `PublishAsyncComplete` within `CORE_PUBLISHER_DRAIN`) → state clear queue (drains within 1s; the rest is left to the sweeper) → slot release → clients. All of it fits within `CORE_SHUTDOWN_BUDGET`: the default plan is 26.2s of 28s, so raising any stop phase needs a higher budget and compose `stop_grace_period` (33s).
- `/app probe` is the container healthcheck.
- `/app resync` and `/app recount -room ID [-dry-run]` are one-shot subcommands: Mongo + NATS only, same config and redaction as serve. `recount` prints `room=… stored=… counted=…`; without `-dry-run` it CASes `member_count_ver` with `rooms` bit 2 (a miss exits with an error, run again), publishes `member_count_changed` and clears the bit after the PubAck. It writes even when the count is already right.
- Every log line goes through a handler that redacts MONGO_URI and NATS_URL credentials, the Mongo password and both Redis passwords.

**Shard-readiness rules (design §5.1).** Mongo runs as a replica set without sharding, but sharding must later need configuration only:
- Large collections use a room-prefixed `_id`; the future shard key is `{_id: 1}`. The 2026-10-14 two-shard try showed this keeps a room on one shard only for fixed-length keys (`messages`, `message_edits`, `pin_actions`, `reply_threads`); `members`, `message_interactions` and `mentions` end in a 1–64-byte id and BinData compares length first, so they scatter (shard key open, D140).
- Every query on `messages` carries the room prefix, and `messages` has no secondary index except the partial `state_pending {_state_at: 1, _id: 1}` (only docs with a pending event, usually a few dozen; D148; once sharded the sweeper asks every shard). Small fact collections (`message_edits`, `pin_actions`) may have `{room_id, created_at}` (D70).
- No multi-document transactions, with one exception (D100): commands that touch an owner run one MongoDB transaction over the room's `members` docs and its `rooms` doc (`$inc owners_ver`), once, a conflict returns `UNAVAILABLE`. No `$lookup` into large collections. Bounded point lookups are fine; unbounded joins are not.
- `message_interactions` and `mentions` are clustered with `_id` prefixed by the message key, so one message's interactions and mentions sit on one shard under the future shard key `{_id: 1}`; their user/target/room/resync indexes (`{tenant, actor_id, …}`, `{tenant, target, …}`, `{room_id, kind, …}`, `{room_id, target, thread_root, seq}`, `{message_key}`, `{room_id, kind, updated_at}`) scatter-gather once sharded (D112, D115, replaces `reactions` of D88). `room_dms` gives one DM per user pair through `_id` alone (D117).
- `members` is clustered with `_id` = room + user; "rooms of a user" is its `{tenant, user_id, state, room_id, joined_at, cleared_at, read_seq, pinned_at, archived_at}` index (no `user_rooms`, D98), which scatter-gathers once sharded by room.
- Never send `_id $in` (or an `$or` of `_id` equalities, which the planner folds into `$in`) to a clustered collection: Mongo runs it as one scan from the smallest to the largest key, across rooms and key lengths (20 rooms of the bench: 320,040 docs read for 100). Build the filter with `mongostore.boundedIDs` (`$or` of `{_id: {$gte, $lte}}` per key or per run of consecutive keys, equality for one key), put extra predicates inside each branch and never sort on the server (sort in Go); a sort or a predicate outside the `$or` turns it into a `COLLSCAN` (D139). The explain itest `bounded_lookup_integration_test.go` guards every call site.
- The URI, read preference and write concern come from config.
- Collections are created only in the bootstrap step.

**Testing conventions.**
- Packages with goroutines use `testing/synctest` and `goleak`.
- Unit tests use miniredis. Call `testlog.SilenceRedis()` in TestMain when dials fail on purpose.
- No short real-time polls: on the dev VM, CPU clocks skew by up to ~7ms and timers wake up to ~36ms late. Wait on explicit signals instead.
